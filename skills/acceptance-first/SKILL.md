# 受け入れテストを先に固定する

このリポジトリでは、人間は diff を読まない。人間が確認するのは、実装前の仕様と、実装後の動作だけである。そのため「何を作るか」を実装の前に人間と合意し、合意した内容を後から動かせないようにする。

承認を得る前に実装を始めない。実装してから仕様やテストを合わせると、テストは実装の追認になり、誤りを検出できなくなる。

## 1. 仕様を書く

`.merge-gate/spec.md` に次の項目を書く。このファイルはコミットしない。

```markdown
## 要件
<何を、なぜ変えるか。依頼の言葉をそのまま写さず、決まったことを書く>

## 受け入れ条件
1. <外から観察できる結果で書く。「〜したとき、〜になる」>
2. ...

## 対象外
<今回は変えないと決めたこと>

## 確認できていない前提
<推測で置いた前提。なければ「なし」>
```

受け入れ条件は、テストで合否を決められる形で書く。「使いやすくする」「適切に処理する」のように合否が決まらない条件は、観察できる結果に書き直す。書き直せない場合は、その点を利用者に質問する。

正常系だけでなく、依頼から読み取れる異常系と境界値も条件にする。空の入力、上限、権限のない利用者、失敗時の挙動が該当する。

## 2. 受け入れテストを書く

受け入れ条件 1 つにつき、少なくとも 1 つのテストを書く。テスト名には、対応する条件が分かる文を書く。

書いたテストを実行し、**落ちることを確かめる**。実装前に通るテストは、条件を検証していない。落ちる理由が「機能がまだない」ことであり、構文エラーや設定の誤りではないことも確かめる。

既存のテストを変更する必要がある場合は、変更の前に、どのテストをなぜ変えるかを利用者に説明する。

## 3. 変更箇所の既存の挙動を固定する

変更する関数やモジュールを呼び出している箇所を調べ、その挙動を検証する既存のテストがあるかを確かめる。

テストがない、または薄い場合は、**現在の挙動をそのまま固定するテスト**を先に書く。このテストは実装前に通ることを確かめる。実装後もこのテストが通り続けることが、デグレがないことの根拠になる。

古いコードでテストが書けない場合は、書けなかった箇所を記録しておき、PR の「検証できなかったこと」に書く。

## 4. 人間の承認を得る

仕様と、書いたテストの一覧を利用者に示し、承認を求める。次の点を伝える。

- 受け入れ条件と、それぞれに対応するテスト
- 推測で置いた前提
- 既存の挙動を固定できなかった箇所

承認が得られるまで実装しない。修正を求められたら、仕様とテストを直して再度示す。

## 5. 承認された内容を記録する

承認を得たら、仕様と受け入れテストを記録する。

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/lock.sh" add .merge-gate/spec.md <受け入れテストのファイル>...
```

記録したファイルは、以後、編集のたびに利用者への確認が入る。作業の終了時にも、記録した内容から変わっていないかが照合される。

## 6. 実装する

受け入れテストが通るように実装する。作業を終えようとすると、`.merge-gate.json` に書かれた検査が自動で実行され、通るまで終了できない。

実装中に、仕様やテストのほうが誤っていると分かった場合は、黙って直さない。何が誤っていたかを利用者に説明して承認を得てから直し、`lock.sh add` で記録し直す。

テストを通すために、テストを緩める、skip する、例外を握りつぶす、といった対処はしない。

## 7. 引き継ぐ

受け入れテストと検査がすべて通ったら、`merge-gate:handoff` の手順で PR を準備する。
