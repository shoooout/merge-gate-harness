# 検証を受けて人間に引き継ぐ

人間は diff を読まずに動作確認をする。PR の本文が、人間にとって唯一の手がかりになる。何を確認すればよいか、どこまで検証できていて、どこからができていないかを、正確に渡す。

## 1. 検査を通す

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/checks/verify.sh"
```

失敗があれば、原因を直してから先へ進む。

次に、検査が通らないまま作業の終了を許された記録が残っていないかを確かめる。

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/checks/unresolved.sh"
```

何も出力されなければ、記録はない。出力された場合は、その検査がいまも通っていない。原因を直して、上の検査が通ることを確かめる。直せない場合は、出力をそのまま PR の「検証できなかったこと」に書く。要約したり、直ったことにしたりしない。

## 2. 独立した検証を受ける

次の 2 つの sub agent を並列に起動する。

- `merge-gate:spec-auditor` に、仕様ファイルのパスと比較元の ref を渡す
- `merge-gate:security-reviewer` に、比較元の ref を渡す

**渡すのはこの情報だけにする。** 実装の説明、変更の要約、「ここは意図的である」といった補足を渡さない。実装者の説明を読んだ検証役は、その説明に沿ってコードを読み、同じ見落としをする。

**検証役を起動できなかった場合は、起動できなかったと PR に書く。** 自分で差分を読み直した結果や、テストが通ったことを、検証役の結果の代わりにしない。実装した本人の確認は、独立した検証にならない。

## 3. 指摘に対応する

指摘を 1 つずつコードで確かめ、次のどちらかにする。

- **直す。** 直したあとは、1 の検査をもう一度通す。仕様や承認済みのテストに触れる修正は、利用者の承認を得る
- **直さない。** 指摘が誤りである、または今回の対象外であると判断した場合は、その理由を PR の「検証できなかったこと」に書く。検証役が付けた確からしさも、そのまま添える

指摘を黙って捨てない。直さなかった指摘は、人間が判断できるように必ず PR に残す。

## 4. 人間の確認が必要かを判定する

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/checks/classify.sh"
```

何も出力されなければ、この変更は diff を読まずにマージできる区分である。理由が出力された場合は、人間が diff を確認する必要がある。出力された理由をそのまま PR に書く。

理由を消すために変更を小分けにしたり、パスを移したりしない。判定を変えたい場合は、利用者に相談する。

## 5. 人間に渡す手順を、先に自分で実行する

PR に書く「動作確認の手順」を、人間に渡す前に自分で実行する。対象は、受け入れ条件ごとの手順と、「影響範囲」に挙げる周辺機能の確認である。実物を動かす。画面なら画面を開き、API なら呼び出し、コマンドなら実行する。

手順ごとに、次のどちらかを残す。

- **実行した。** 実行したコマンドか操作と、観察した結果を残す。結果は、出力のうち合否が分かる行を引用する。「問題なかった」のような要約にしない
- **実行できなかった。** 理由を残す。環境がない、ログインの手段がない、外部のサービスに届かない、破壊的な操作になる、などである

テストや型検査が通ったことは、ここでの証拠に数えない。それらは別に確かめられている。ここで確かめるのは、利用者が触る実物が、仕様どおりに動くことである。

実行して手順どおりにならなかった場合は、原因を直して 1 の検査からやり直す。結果を書き換えて合格にしない。

### 実行の準備には、すでにあるものを使う

**検証のためにアプリを変えない。** 仕様にない seed、検証用のアカウント、ログインを省く経路を、この変更に足さない。ログインを省く経路は、本番に残ればそのまま侵入口になる。足りないものがあって実行できない手順は、「実行できなかった」として理由を残す。

ログインが要る手順では、次の順に手段を探す。

1. **リポジトリにすでにある手段を使う。** 既存の seed、fixture、文書に書かれた開発用のアカウントである
2. **手元の環境で、アプリがもともと持っている経路からアカウントを作る。** 登録の画面や、既存の管理用のコマンドである
3. **人間がすでにログインしているブラウザを使う。** 使ってよいのは、手元の環境と検証用の環境だけである。ログインされていなければ、利用者にログインを頼む。利用者が応答できない状況で実行されている場合は、待たずに「実行できなかった」とする

3 では、ログインした人間の権限がそのまま渡る。手順に書いた操作のほかは行わない。

どの手段を使う場合も、次のことを守る。

- `.env` や鍵のファイルから、ログインに使う値を読まない
- 利用者のパスワードや認証コードを尋ねない。入力は利用者が自分で行う
- 本番の環境にログインしない
- 引用する結果に、トークン、Cookie、セッションの識別子、個人情報を含めない

## 6. PR の本文を書く

人間は本文を上から読み、途中で読むのをやめる。先頭の「要点」だけで、何を確認すればよいかが分かるように書く。

次の節を、この順で必ず含める。CI は「要点」以外の節の有無と中身を検査する。リポジトリに PR の書式の決まりがある場合は、その書式にこれらの節を加える。

````markdown
## 要点
- <何を変えたか。利用者から見た挙動で 1〜2 行>
- <人間に確認してほしいこと。最も重要な 1〜3 件>
- <検証できなかったことと、人間の確認が必要な理由。どちらもなければ、この行を書かない>

## 仕様
<details>
<summary>承認済みの仕様の全文</summary>

<.merge-gate/spec.md の全文。見出しを 1 段下げて「### 要件」「### 受け入れ条件」のようにする>

</details>

## 動作確認の手順
1. <人間が実際に行う操作と、何が見えれば合格か>

## 実行した確認
- 手順 1: <実行したコマンドか操作> → <観察した結果。出力のうち合否が分かる行>
- 手順 2: 実行できなかった。<理由>

## 影響範囲
- <今回の変更が挙動を変える画面、API、バッチ、データ。変更した処理を呼び出している側も含める>

## 独立した検証
- spec-auditor: <実行した。指摘 n 件のうち、直した n 件、直さなかった n 件 | 実行できなかった。理由>
- security-reviewer: <同上>

## 検証できなかったこと
- <テストを書けなかった箇所、実行できなかった検査、直さなかった指摘とその理由と確からしさ。なければ「なし」>

## 人間の確認が必要な理由
<classify.sh の出力。出力がなければ「なし」>

<change-id.sh が出力した行>
````

書くときの基準は次のとおりである。

- **要点**は 5 行以内にする。下の節の言い換えを並べず、人間が次に取る行動を決めるのに要る事実だけを書く
- **仕様**は、承認された `.merge-gate/spec.md` を省略も要約もせずに載せる。8 つの節と、条件ごとのテストの名前を、そのまま残す。CI は PR の本文から仕様を読み、条件に書かれたテストが追加されているかと、仕様に挙げていない既存テストの変更がないかを確かめる。仕様のない PR は CI で落ちる。全文は長いので `<details>` で折りたたむ。`<summary>` の行のあとと `</details>` の行の前を 1 行ずつ空ける。空けないと、GitHub が中の見出しを Markdown として表示しない
- **動作確認の手順**は、受け入れ条件ごとに書く。正常系を 1 回触るだけの手順にしない。異常系と、「影響範囲」に挙げた周辺機能の確認も含める。1 つの手順は、操作と合格の基準を合わせて 1〜2 行にする
- **実行した確認**は、5 で残した結果を、手順の番号に対応づけて書く。1 項目を 1〜2 行にする。実行できなかった手順は、ここに理由を書く。人間は、ここに「実行できなかった」とある手順を重点的に確かめる。1 つも実行できなかった場合も節を残し、その理由を書く
- **影響範囲**は、変更したファイルの一覧ではなく、利用者から見て挙動が変わる場所を書く
- **独立した検証**は、検証役ごとに、実行したかどうかと、指摘の件数と扱いを書く。指摘の内容はここに書かない。直さなかった指摘は「検証できなかったこと」に書く
- **検証できなかったこと**を空にするために、確かめていないことを確かめたように書かない。ここが正確であることが、人間の動作確認の範囲を決める

本文を短く保つために、次のことを守る。削ってよいのは言い回しであり、事実ではない。

- 仕様のほかは箇条書きにし、1 項目を 1〜2 行にする
- 同じ事実を 2 つの節に書かない。仕様に書いてある内容を、ほかの節で言い直さない
- 実装の経緯、diff の説明、試してやめた方法を書かない。人間は diff を読まないので、動作確認に使えない情報は読む時間を奪うだけである
- 「検証できなかったこと」は、長くなっても削らない

本文の最後には、検証した変更の識別子を置く。次のコマンドが出力する行を、そのまま写す。

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/change-id.sh"
```

識別子は、この本文の検証の結果が、どの変更に対するものかを示す。CI は PR の変更から同じ識別子を計算し、一致しなければ失敗にする。

識別子は、コミット前の変更と、git に追加していないファイルも含めて計算される。PR に入れないファイルが作業ツリーに残っていると、CI の計算と一致しない。識別子を取る前に片づける。

## 7. 本文を検査する

本文をファイルに書き出して検査する。CI も同じ 2 つを実行する。ファイルはリポジトリの外に置く。リポジトリの中に置くと、そのファイルも変更として数えられ、識別子が一致しなくなる。

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/checks/spec.sh" <本文のファイル>
bash "${CLAUDE_PLUGIN_ROOT}/scripts/checks/handoff.sh" <本文のファイル>
```

## 8. PR を作る

commit、push、PR の作成は、利用者の指示とリポジトリの決まりに従う。指示がなければ、準備した本文を示して指示を待つ。

## 9. PR を作ったあとに変更を足したら、検証をやり直す

変更を足すと識別子が変わり、CI が失敗する。本文の検証の結果が、足した変更を見ていないためである。CI の失敗への対応や、レビューを受けた修正も、足した変更に当たる。

1 から 5 をやり直し、本文を書き直して、識別子を取り直す。push の前に、PR の本文を更新する。CI は、push の時点の本文を検査する。

**検証をやり直さずに、識別子だけを書き換えない。** やり直さなかった確認や検証があるなら、その項目に、足した変更を見ていないことを書く。たとえば「security-reviewer: 実行した。そのあとに足した文言の修正は見ていない」と書く。

base ブランチが進んだだけでは、識別子は変わらない。base ブランチを取り込んだ場合は、このブランチが変えたファイルを base ブランチも変えていたときにだけ変わる。
